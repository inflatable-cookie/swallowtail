# Nucleus Observable-Activity Handoff

Status: bounded non-published `0.1.0` handoff
Consumer authority: Nucleus

This handoff describes an additive projection over existing prepared operations
and runtime streams. It changes no Nucleus source and authorizes no product,
persistence, retention, or presentation policy.

## Public Inputs

For the selected prepared run or session operation, inspect:

```rust
let profile = prepared.evidence().operation().observable_activity();
```

Some facades return `PreparedOperationEvidence` directly from `evidence()`;
adapter-local evidence wrappers expose it through `operation()`. Nucleus does
not need a provider-native event type or raw payload in either case.

Then consume `RuntimeEventKind::Activity` on the existing ordered run or turn
stream. `RuntimeEventKind::OutputAvailable`, callbacks, direct-tool calls,
terminal outcome, and joined cleanup remain separate.

The compile-checked
[Nucleus projection example](../../crates/swallowtail-runtime/examples/observable_activity_nucleus.rs)
uses only public `swallowtail-runtime` APIs.

## Preparation Decision

`ObservableActivityProfile::availability()` has three exact outcomes:

| Outcome | Nucleus posture |
| --- | --- |
| `Available` | Render only the kinds, lifecycle, content, and correlations the exact profile declares. |
| `Unavailable` | Keep the operation usable and show final output. Do not synthesize generic work. |
| `NotApplicable` | Treat the prepared role as non-ordinary activity, such as catalogue, serving, or realtime media. |

Inspect lifecycle per kind. `CompletionOnly` is valid support, not a failed rich
stream. Do not invent starts or updates. An unverified-newer interface retains
the last qualified profile and cannot widen it from newly observed fields.

Nucleus may require exact `ObservableActivity` constraints during preflight.
It may instead accept a thinner profile and render only emitted observations.
This is a product decision, not provider routing.

## Durable Projection Boundary

Nucleus owns two separate durable projections:

1. assistant messages
2. work activity

Keep Swallowtail identity intact in both:

- consumer thread identity
- runtime run or turn identity from `ActivityOperationId`
- operation-local `ActivityId`
- runtime event sequence
- activity kind, lifecycle phase, and status
- assistant phase where applicable
- content change and content stream where disclosed
- optional provider display label
- optional callback, direct-tool, or provider-request correlation

Do not use a provider label as identity. Do not reconstruct identity from
content. Treat activity content as task data, not diagnostic text.

`AssistantMessage` observations project to the message side. All other
activity kinds project to the work side. A provider-unspecified assistant
phase remains provider-unspecified; do not label it commentary or final.

`ReasoningSummary` means client-visible summary or thought text only. UI copy
must not call it complete reasoning, chain-of-thought, a scratchpad, or hidden
model reasoning.

## Grouping And Collapse

Grouping is a view over durable work records, not a rewrite of Swallowtail
identity. Nucleus may collapse adjacent work observations when they:

- belong to the same consumer thread and runtime turn
- remain consecutive in runtime event order
- are not separated by an assistant message or final output

Keep each activity id and lifecycle record underneath the group. Correlated
callback and direct-tool exchanges stay separately actionable even when their
display rows are collapsed. Unknown namespaced activity remains visible as
unknown work or is omitted under explicit product policy; it does not become
empty generic progress.

## Final Output

Final operation output remains distinct from completed final-assistant
activity. Nucleus may deduplicate presentation, but must not discard either
semantic record merely because their text matches.

Terminal outcome and event-stream completion still decide operation state.
The last activity observation does not prove terminal success or cleanup.

## Migration Boundary

For a migrated route:

- remove consumer switches on provider-native event names
- stop deriving tool identity or status from raw provider payloads
- replace broad generic progress with typed activity or no work row
- keep callback and direct-tool handling on their existing exchanges
- keep thread lifecycle, authorization, review, retention, deletion,
  analytics, and UI in Nucleus

Provider-specific gaps remain visible through the prepared profile and the
[activity matrix](../guides/provider-solution-activity-matrix.md). Do not fill
them with another route, a fallback transport, or inferred lifecycle.

## Consumer Acceptance

A later authorized Nucleus implementation should prove:

1. rich lifecycle, completion-only, unavailable, and not-applicable profiles
2. assistant messages and work activity persist separately
3. repeated updates preserve one activity identity
4. consecutive work groups without losing underlying lifecycle
5. reasoning is labelled only as a summary
6. callback and direct-tool correlations remain actionable
7. final output remains usable when all activity is ignored
8. provider-unspecified and unknown activity are not overclassified
9. cancellation, failure, terminal outcome, and cleanup remain independent

No Nucleus edit, package publication, release, or provider effect is part of
this handoff.
