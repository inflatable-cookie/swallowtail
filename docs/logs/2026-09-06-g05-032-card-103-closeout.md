# g05.032 Card 103 Closeout

Card 103 answered the OpenCode cancellation-cleanup abort as fixture-only and
repaired the fixture. Production source is unchanged, so this is not `v0.4.2`
content and card 101 is unblocked on this card.

## Verdict: Fixture, Not Production

The failing assertion names a DELETE, but the gate in that test fires on
`GET /session/status?` (`tests/http_support/handlers.rs:53`); the catalogue
path issues no DELETE at all. The stall is the fixture's own deadline budget.

`deadline_after(Duration::from_millis(10))` at the old
`tests/prepared_facade/session_import.rs:299` builds a wall-clock deadline
10 ms ahead of `TestClock::now()` (`tests/prepared_facade/fixture.rs:323`,
elapsed milliseconds). The driver refuses to dispatch a request whose deadline
has already passed (`src/driver/provider_session_import.rs:196-197`) and
returns `timed_out()`. Reaching `/session/status` costs a thread spawn, lease
acquisition, and a full loopback health round trip. Measured margin on an
18-core host under 20 CPU burners and 20 concurrent binaries: 2-4 ms. A macOS
CI runner is comfortably 3x slower, so the pre-dispatch expiry check wins at
roughly even odds, the operation ends `TimedOut` before any dispatch, and the
test's `wait_for_dispatch()` waits out the 120 s hang guard.

That production behaviour is correct: an expired deadline must not dispatch,
and `access.release(&services)` still runs on every path
(`src/driver/provider_session_import.rs:64` and `:107`), so leases are always
released. The Review Oracle invariant holds; the fixture assumed a dispatch the
driver is entitled to skip.

## Correction To The Card

The abort was not `resume_unwind`. The hang-guard assert panics while holding
the gate guard, which poisons the mutex; `FixtureServer::drop` then called
`DeleteResponseGate::release`, whose `.expect("...poisoned")` raised a second
panic during unwinding — non-unwinding, so SIGABRT. Both panic sites in the CI
logs are on the test thread: `delete_gate.rs:41` is `wait_for_dispatch`,
`delete_gate.rs:51` is the poisoned lock in `release`. The `resume_unwind` in
`Drop` was already guarded by `!thread::panicking()` and never fired.

## Repair

- The gate locks poison-tolerantly, so a hang-guard expiry can never turn into
  a second panic during teardown.
- `FixtureServer::drop` records the fixture-thread panic and reports it, and
  never raises one. `FixtureServer::shutdown` is the explicit non-`Drop`
  teardown that resumes it; the gated tests call it. The non-`Drop` handler
  join at `tests/http_support/mod.rs` keeps its resume behaviour.
- Manual-trigger deadline tests take `PreparedFixture::manual_deadline`, a
  budget no loaded host reaches, so the armed trigger is the only expiry.
  This also removes the same class from the delete deadline test's 1 s budget.

One `resume_unwind` remains reachable from a `Drop`: the `JoinOnDrop` guard
inside `fixture_join_suppresses_secondary_panic_during_existing_unwind`. That
is the test that pins the `!thread::panicking()` suppression the card asked to
keep, not a fixture teardown path. Flagged for the reviewer rather than
removed.
