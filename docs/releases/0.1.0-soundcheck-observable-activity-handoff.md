# Soundcheck Observable-Activity Handoff

Status: bounded non-published `0.1.0` handoff
Consumer authority: Soundcheck

This handoff keeps Soundcheck's bounded structured-run result independent from
optional intermediate activity. It changes no Soundcheck source and
authorizes no product progress, evidence, review, or persistence policy.

## Public Inputs

Inspect the selected prepared structured operation's
`PreparedOperationEvidence::observable_activity()` before effects. Consume
`RuntimeEventKind::Activity` from the same ordered run stream when product
progress needs it.

The compile-checked
[Soundcheck projection example](../../crates/swallowtail-runtime/examples/observable_activity_soundcheck.rs)
uses only public `swallowtail-runtime` APIs.

No provider-native event switch or raw payload parser is required.

## Minimal Adoption

Soundcheck may ignore every activity event. Final output remains on
`RuntimeEventKind::OutputAvailable`; terminal outcome and joined cleanup retain
their existing meanings.

If Soundcheck exposes progress, project only:

- composite activity key
- portable activity kind
- exact lifecycle phase
- optional bounded provider label

Use disclosed content only when the product needs it and the exact prepared
profile permits it. Activity content is task data and must not enter stable
diagnostics.

Never persist by operation-local activity id or provider activity reference
alone. Both may repeat in another run. `ActivityKey` binds the consumer-unique
runtime run owner to that local id; Soundcheck retains its own evidence and
result identities separately.

`Unavailable` means final-output-only operation progress. `CompletionOnly`
means a valid terminal observation without a synthetic start. `NotApplicable`
belongs to a different operation role and is not structured-run progress.

## Reasoning And Tools

`ReasoningSummary` is provider-intended readable summary text. Never present it
as hidden reasoning or complete chain-of-thought.

Harness-owned tool activity is display evidence, not a request for Soundcheck
to execute a tool. Callback and direct-tool exchanges remain their existing
typed control paths. Correlated activity does not replace either exchange.

## Migration Boundary

For a migrated structured route:

- remove provider-native event parsing from Soundcheck
- replace generic progress parsing with typed activity or no progress
- retain final structured output as the acceptance input
- retain Soundcheck-owned evidence, validation, repair, ranking, review,
  persistence, analytics, and UI
- preserve exact route gaps from prepared evidence

No route fallback or provider inference is added. A route with thinner
activity remains usable when its final output satisfies Soundcheck.

## Consumer Acceptance

A later authorized Soundcheck implementation should prove:

1. final output is unchanged when all activity is ignored
2. optional progress uses portable kinds and exact lifecycle only
3. repeated local/provider ids under different runs retain distinct keys
4. completion-only activity creates no invented start
5. unavailable activity creates no generic progress
6. reasoning-summary language remains exact
7. callbacks, terminal outcome, and cleanup remain independent

No Soundcheck edit, package publication, release, or provider effect is part
of this handoff.
