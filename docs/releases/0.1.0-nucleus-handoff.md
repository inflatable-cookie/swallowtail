# Nucleus Swallowtail 0.1.0 Handoff

Status: active non-published candidate handoff
Consumer authority: Nucleus

Nucleus already uses the Codex prepared integration in its sibling-source
development path. Candidate adoption changes only the dependency source; it
does not reintroduce manual preflight assembly.

## Dependency Change

Nucleus currently consumes these packages from a sibling checkout:

- `swallowtail-core`
- `swallowtail-runtime`
- `swallowtail-host-local`
- `swallowtail-adapter-codex`

The release adoption shape replaces each path dependency in
`nucleus-agent-adapters` with exact candidate version `=0.1.0`. Exact pins keep
the first consumer rollout separate from later compatible Swallowtail patches.

Before publication, isolated validation uses `[patch.crates-io]` entries
pointing to the four extracted candidate archives. After publication, Nucleus
removes those temporary patches and resolves the same exact versions from
crates.io.

## Prepared Normal Path

Nucleus selects the Codex app-server driver and one host-approved executable,
then calls `prepare_codex`. It uses separate named profiles:

- `prepare_catalogue` for model discovery
- `prepare_read_only_session` for chat
- `prepare_bounded_workspace_session` for explicitly authorized task work

The profiles retain exact executable-version assessment, access provenance,
the immutable plan, and matching runtime request. Typed catalogue, open,
resume, and close lifecycles remain distinct. Bounded workspace access is
explicit and never replaces the read-only default.

Nucleus retains prompts, model choice, tools, callback authorization,
workflows, task policy, persistence, and UI. Swallowtail discovers no implicit
provider, model, credential, executable, endpoint, or sandbox.

## Minimum Toolchain And Target

- consumer minimum for these four packages: Rust `1.93`
- candidate current-stable validation: Rust `1.97.1`
- verified target: Apple Silicon macOS
- other targets and toolchains: unverified, not prohibited

## Relevant Provider Guarantees

Nucleus uses the Codex app-server route for catalogue, chat, and bounded task
sessions.

- app-server v2 maintained: `0.110.0..=0.146.0`
- app-server deprecated: `0.80.0..=0.81.0`, `0.84.0..=0.107.0`
- stable versions above `0.146.0`: executable only as visible unverified-newer
  attempts, not guaranteed support
- gaps, exclusions, malformed versions, and unqualified prereleases: rejected

The crate upgrade grants no provider access or sandbox guarantee.

## Validation

Candidate proof uses a temporary copy of Nucleus's current tracked and
untracked non-ignored source state. It:

1. replaces the four path dependencies with exact `=0.1.0` requirements
2. patches crates.io to the extracted candidate packages
3. preserves the existing lockfile
4. runs `cargo test -p nucleus-agent-adapters swallowtail_codex:: --locked`

The original Nucleus worktree and lockfile remain untouched.

Expected deterministic evidence is 15 passing Swallowtail Codex tests with two
installed/live probes ignored. The same package candidate also passes the
93-test packaged Codex lifecycle suite.

For consumer-owned adoption, Nucleus should additionally run its normal
`effigy check:rust`, focused adapter tests, and `effigy qa` before merging.

## Rollback

There is no prior published Swallowtail version.

Rollback restores Nucleus's pre-adoption manifest and lockfile, then restores
the four sibling path dependencies. For an exact source rollback, extract the
active or superseded source bundle named by its `candidate.env` and point the
paths at its four crate directories.

Do not silently fall back from a failed registry resolution or incompatible
Codex observation. Rollback is a consumer-owned manifest and lockfile change.
